# Reduced disk mode

The desktop app now has an engine choice: **Reduced disk · Chudnovsky + packed YCD**.

Automatic mode also tries this reduced/packed plan when the normal native plan exceeds available disk. It starts nothing if neither plan fits the free-space check.

This uses y-cruncher's real `chudnovsky-reduced` algorithm and writes decimal `.ycd` directly. YCD stores 19 digits per 8-byte word, so 62,831,853,071 digits require about **24.64 GiB** of payload instead of **58.52 GiB** of text. Header/alignment overhead is small. It trades some arithmetic speed for reduced working storage; it does not promise that searches of compressed data are faster than searches of raw ASCII.

The explorer reads YCD files directly for digit windows, text, colors, pixels, statistics, searches and sampled zoom/pan tiles. It does not create a complete text expansion. Packed searches use the bounded streaming path; raw text retains the existing native zero-copy scanner. Exporting a text file is optional and requires additional disk space.

## The 62.83B target: actual native planning, no full computation

The installed y-cruncher 0.8.7.9547b was opened at its configuration menu and loaded with the exact target **62,831,853,071**, reduced Chudnovsky, hexadecimal output disabled, output verification enabled, checkpoints disabled, and 256 MiB working RAM.

It reported:

- Logical working disk: **269 GiB**.
- Compressed decimal output: **24.6 GiB**.
- Combined conservative native requirement: about **293.6 GiB**, before reserve.

Task decomposition 1 and 8 both reported the same storage figure. Changing thread count did not make this plan smaller. The Start Computation option was never selected for this target.

About **276.5 GiB** was free during the check. Therefore this native plan is **not verified to fit** the current drive. It might have a smaller measured peak because the worst working and output allocations need not overlap, but that is not a safe completion guarantee. The app keeps its free-space checks and will not silently claim that a smaller estimate makes the job fit.

The app's reduced-mode estimate includes additional headroom beyond the native menu and the existing 2 GiB reserve. On this machine, clearing approximately **25 GiB more** would pass that conservative app check, provided other usage does not increase. This is an estimate, not a promise about a complete large run. A second drive is another option.

Your previous observation of about 127 GB extra usage for 27.18B is useful empirical evidence, but it is not an upper bound for a different precision/algorithm/format. The recorded old native menu estimated 128 GiB working disk plus 25.3 GiB output for that run, illustrating the difference between conservative logical estimates and a sampled physical peak.

## Checks performed

- A real **1,000,000-digit** run of the complete reduced/YCD pipeline was performed and its entire decoded output compared with independent MPFR digits.
- The native packed file was **421,888 bytes**, versus 1,000,002 bytes for a prefixed text file.
- Tests cover unaligned reads across 19-digit words, leading zeros, tail windows, text/pixel encodings, sampled tiles, packed searches, malformed/truncated files, cache selection, native configuration and committing YCD without a text copy.
- Output verification and swap checksums remain enabled.
- Existing 27.18B and 1B digit files were not converted, deleted, or changed.
- No 62.83B or 200B calculation was started.

The public website currently continues to serve your existing raw 27.18B dataset. This change is to the desktop calculator/explorer; selecting a future new dataset for the public host is a separate step.
